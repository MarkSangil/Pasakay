# 1 · Project Overview

**PASAKAY** is a mobile application system developed by Grade 12 STEM students
of La Salle College Antipolo as an academic research project (School Year
2026–2027). "Pasakay" is Filipino for "to hoist/assist onto a ride". The system
supports **SSLTODA** — the Special Local Tricycle Operators and Drivers'
Association of Barangay San Luis, Antipolo City — which operates tricycles from
five terminals in the barangay.

## The problem it addresses

Before this system, a commuter in Barangay San Luis had no reliable way to
reach the right tricycle driver. Drivers rotate through shifts at five
different terminals, so a commuter who needs a ride at a specific time would
have to physically go to a terminal and guess which drivers are on duty. There
is no public directory of drivers, no record of who handles which shift, and
no research data about how commuters actually contact drivers.

PASAKAY turns the association's paper roster into a searchable digital
directory. A commuter selects a terminal, sees the drivers assigned to that
terminal and the current shift, and can contact them by tapping a button that
opens the phone's own dialer or SMS app. The system records usage so the
research team can evaluate how the association's services are used.

## Who uses it

| Role | Who | What they do |
|---|---|---|
| **Commuter** | Residents and visitors of Barangay San Luis | Register (pending admin approval), browse terminals, view drivers per shift, call/SMS drivers, request rides, rate drivers, receive notifications |
| **Driver** | Registered SSLTODA members mapped to one terminal and one shift | Log in with mobile number + password, accept or reject ride requests, complete or dispute trips, request shift changes, read reviews |
| **System admin** | The research team's designated administrator | Approve accounts, manage drivers/commuters/terminals/shifts, resolve disputes, moderate reviews, log privacy requests, monitor usage and audit logs |

## The applications

All three share one Supabase backend:

1. **Pasakay driver app (`apps/driver`)** — Android APK. Drivers sign in with
   their registered mobile number and password.
2. **Pasakay customer app (`apps/customer`)** — Android APK. Commuters sign in
   with their registered mobile number and password.
3. **Pasakay admin console (`apps/admin`)** — a web app deployed to GitHub
   Pages at `https://marksangil.github.io/Pasakay/`, for the research team.

## What is actually implemented (verified in code)

- Account registration with server-side validation; accounts start
  `pending_verification` and must be approved by the admin before login.
- Login via mobile number + password (converted internally to a Supabase Auth
  email identity), with a pre-login status gate for pending/suspended accounts.
- Driver directory browsing: terminals → shifts → drivers, with the driver's
  TODA plate number, rating, and current terminal.
- Direct contact via the device's Phone and SMS apps (passthrough, not
  in-app calling).
- Ride request lifecycle: request → driver accepts/rejects → booking with
  status tracking → completion, dispute (flag), or passenger report →
  driver rating from reviews.
- Reviews: one per completed booking, 1–5 stars plus optional text, with
  driver-reported review reports.
- Notifications both in-app (Supabase Realtime) and push (Firebase Cloud
  Messaging through Supabase Edge Functions).
- Schedule-driven shift reminders and change notifications generated by
  database triggers and a scheduled job.
- A system admin console covering: overview metrics, driver CRUD + TODA
  verification, commuter access control, terminal and shift management
  (including shift-change requests), booking settings, review moderation,
  dispute resolution, and usage/audit monitoring.
- Foreground-usage tracking (sessions + heartbeats) for both passenger and
  driver apps, and an action audit log (which screens and key actions were
  used) for research evaluation.
- Legal texts (Terms, Privacy Policy) built into both mobile apps, including
  research-team contact details and a consent flow at signup.

## What the system deliberately does not do

These exclusions are stated in the in-app Terms and Conditions and match the
code — they are design decisions, not failures:

- **No GPS tracking, navigation, or fare computation.** The apps never read
  the device location permission and never track any vehicle.
- **No online booking or digital payment.** The apps do not collect money.
- **No in-app calls or stored messages.** Communication is handed off to the
  device's own apps; only the fact that a contact action was used is logged
  (an action name and timestamp, never message content or call audio).
- **No government/agency data feeds.** Driver verification (TODA plate and
  identity) is a manual administrative check against the association's own
  records, as documented in the migration file.

## Technologies and services (verified versions)

| Technology | Role |
|---|---|
| Flutter (Dart SDK ^3.13.2) | all three apps, one codebase each target |
